    Why ULP Data Differs from DW — Architecture Analysis

    This document explains how ULP stream data is generated from GraphQL subgraph definitions, and why it structurally differs from DW_LSTG_ITEM. Evidence is drawn from the 26 subgraph schemas in data/ulp/supergraph/ and 22 stream samples in data/ulp/ulp-sample-data/.

    Part 1 — How ULP Stream Data Is Generated

    1.1 The Pipeline: Seller Action → Stream Event

    The ULP stream JSON (afterchangeDocumentPlain) is not the output of a consumer GraphQL query. It is generated by unilistingsvc as a side-effect of a state change event:

    Seller action / Domain event
    │
    ▼
CLS (Core Listing Service)
    writes NuDoc document families
    (ItemKeyspace.__ROOT__, ItemQtyPrice, BusinessPolicies, etc.)
    │
    ▼
unilistingsvc receives ITEM_REVISED event
    │
    ▼
SVLS subgraph (svls.graphql) called via FGQL
    reads from CLS over authenticated HTTP
    resolves 50+ fields defined in svls.graphql
    │
    ├── Provider subgraphs called in parallel (@requires satisfied):
    │     ITMVZBLIT           → visibilitySummary, visibility
    │     BASICLISTINGDATA    → watchCount, certifiedExpertInsight
    │     MPLS                → shippingProgramEligibility.globalShippingProgram
    │     EBAYPLUSELIGIBILITY → ebayPlus
    │     PICKUPELIGIBILITY   → eligibleForPudo
    │     SAPSVC              → autoTagProduct, dfAnnotatedAspects
    │     CMPLREGULATORYSVC   → itemCountryOfOrigin
    │     MDMLUSVCIO          → markdownDiscountDuration
    │     ITEMCOMPATIBILITYSVC → listingCompatibilities
    │     SEOCORELABSVC       → photosWithAltText
    │     (others per configuration)
    │
    ▼
Composite listing document assembled by MonstorFieldMapper
    (provider-group cache key = listingId)
    │
    ▼
Written to ULP cache (NuKV/NuData/Monstor) as gzip+base64
    │
    ▼
ULP stream event emitted to Kafka:
    {
      "metadata": { id, operation, ulpListingVersionId, ... }
      "beforeChangePatch": [RFC 6902 JSON Patch — exactly what changed]
      "afterchangeDocument": "<gzip+base64 of new state>"
      "afterchangeDocumentPlain": { "listing": { ... } }
    }

    1.2 GraphQL Schema Controls Stream Field Shape

    Every field in afterchangeDocumentPlain.listing is declared in one of the 26 subgraph schemas. The schema directly determines field names, types, and values in the stream:

    Schema construct Effect on stream data
    scalar DateTime ("RFC-3339 compliant") All timestamps are UTC ISO 8601 strings ending in Z
    enum ListingFormat { AUCTION, BIN, CLASSIFIED_AD } listingFormat is always the string enum, never an integer
    enum ListingStatusEnum { ACTIVE, ENDED, SCHEDULED } listingStatus is always the string, never 0/1/4
    enum CreationMode { Add, Relist, SellSimilar, SellOneLikeThis } 20+ DW codes collapsed to 4 values by schema design
    enum ShippingCostPlanType { FLAT, CALCULATED, FREIGHT, ... } costType is always the string, never 1/2/3
    enum PackageType { PackageThickEnvelope, Letter, ... } Package type is always the string, never the integer
    scalar CurrencyAlpha3Code Currency is always ISO 4217 (USD, GBP, EUR), never an integer
    @svlsField(fieldName: "versionId") sellerListingVersionId maps from SVLS field versionId
    @svlsField(fieldName: "lifecycle") listingLifecycle maps from SVLS field lifecycle
    @svlsField(fieldName: "format") listingFormat promoted from SVLS integer field to typed enum
    @fallbackToSource(startDate, endDate) During migration window, reads from CLS live, not NuDoc cache
    @compress Field stored gzip-compressed in provider-group cache
    @ignoreForEventGeneration(eventName) Field excluded from stream event generation

    1.3 Confirmed Observations from 22 Stream Samples

    Observation Sample evidence
    All timestamps end in Z (UTC) "startAt": "2026-09-08T15:55:06.000Z"
    listingFormat is always "BIN" string Never 9 (DW integer)
    listingStatus is "ACTIVE" or "ENDED" Never 0 or 1
    creationMode is always "Add" Even for lstg_mthd_id=19 or =23 in DW
    marketplace uses underscore "EBAY_US" Deprecated marketplaceId uses hyphen "EBAY-US"
    All GTC listings: listingDuration: "GTC" Consistent with gtc_up_flag=1 in DW
    schemaVersion: "2.1.0" on every record Stream envelope version for consumer deserialization

    Part 2 — Six Root Causes of ULP vs DW Differences

    Cause 1 — UTC vs PST/PDT: The DateTime Scalar

    GraphQL evidence (repeated in every schema using DateTime): 

    scalar DateTime
# "A slightly refined version of RFC-3339 compliant DateTime Scalar"

    Sample data confirmation: 

    "startAt": "2026-09-08T15:55:06.000Z",
"endDate": "2026-10-08",
"actualEndAt": "2026-10-08T15:55:06.000Z"

    The Z suffix means UTC. endDate is the date portion of the UTC timestamp. DW stores dates in PST/PDT (eBay's operational timezone) and truncates to a local calendar date.

    Impact by region:

    For a UK listing that started at 2026-04-25T19:34:20 UTC: 

    DW  auct_start_dt = 2026-04-25   (PST truncation — same day)
ULP startDate     = 2026-04-26   (UTC date — next calendar day)

    For a US listing that started at 2026-09-05T17:41:57 UTC (= 10:41 PDT): 

    DW  auct_start_dt = 2026-09-05   (same day in both timezones)
ULP startDate     = 2026-09-05   (match — no offset for US morning listings)

    Pattern: UK, EU, and AU listings listed in the evening local time systematically show ULP date = DW date + 1 day. US listings in the morning show no offset. This is a by-design architectural difference, not a bug.

    Cause 2 — String Enums vs Integer Lookup IDs

    DW was built in the Oracle/Teradata era where integers are cheaper to store and join. ULP's GraphQL schema makes integers impossible — every status, format, and type is a named string enum. No translation lookup tables are needed on the ULP side.

    Full mapping table:

    Concept DW (integer) ULP (GraphQL enum) Schema declaration
    Listing status 0=Live, 1=Ended, 4=Scheduled ACTIVE, ENDED, SCHEDULED svls.graphql: enum ListingStatusEnum
    Listing format 9=Fixed Price, 1=Auction, 13=Classified BIN, AUCTION, CLASSIFIED_AD svls.graphql: enum ListingFormat
    Currency 1=USD, 3=GBP, 5=AUD, 7=EUR USD, GBP, AUD, EUR svls.graphql: scalar CurrencyAlpha3Code
    Shipping cost type 1=Flat, 2=Calculated, 3=Freight FLAT, CALCULATED, FREIGHT svls.graphql: enum ShippingCostPlanType
    Package type 4=PackageThickEnvelope PackageThickEnvelope svls.graphql: enum PackageType
    Unit of measure 1=oz, 2=grams English, Metric svls.graphql: enum UnitOfMeasure
    Marketplace 0=US, 3=GB, 77=DE EBAY_US, EBAY_GB, EBAY_DE svls.graphql: enum ListingMarketplace
    End reason 0=Natural, 2=Not available NONE, NOT_AVAILABLE svls.graphql: enum EndReasonEnum

    DW consumers need joins to DW_CURRENCIES, DW_SITES, DW_AUCTION_CODES. ULP consumers read the value directly.

    Cause 3 — Intentional Granularity Collapse in CreationMode

    GraphQL evidence: 

    # svls.graphql
enum CreationMode {
  Add
  Relist
  SellOneLikeThis
  SellSimilar
}

    DW lstg_mthd_id has 20+ codes tracking the exact tool. ULP's CreationMode intentionally collapses them:

    DW lstg_mthd_id DW meaning ULP creationMode
    1 SYI2 Add
    5 Trading API Add
    19 SYI 3 API / Listing Draft Service Add
    21 EasyLister Add
    23 Listing Draft Service (LDS) Add
    10 Relist as SIF Relist
    11 Sell Like Item SellSimilar

    The @svlsField(fieldName: "format") directive on listingFormat in the schema documents this same pattern — original SVLS field names are preserved for audit while the schema promotes values to typed enums with fewer options.

    All 22 stream samples show creationMode: "Add" regardless of whether DW records lstg_mthd_id = 19 (SYI3) or 23 (LDS).

    Consumer impact: ULP cannot distinguish EasyLister from Trading API from SYI3. Use DW if tool-level analysis is required.

    Cause 4 — Schema Separates Scheduled vs Actual End Date

    GraphQL evidence (ListingLifecycle type in svls.graphql): 

    type ListingLifecycle {
  scheduledEndDate: DateTime   # @deprecated("Use scheduledEndAt") — scheduled end
  scheduledEndAt: DateTime     # @fallbackToSource — canonical scheduled end
  actualEndAt: DateTime        # Actual termination timestamp (separate field)
  endDate: DateTime            # @deprecated — was scheduled end
  startDate: DateTime
  startAt: DateTime
  listingStatus: ListingStatusEnum
  listingDuration: ListingDuration
  onHold: Boolean
}

    DW has a single overloaded field auct_end_dt: - For live listings: = scheduled end date - For ended listings: = actual end date (overwritten when listing ends)

    ULP explicitly separates these. For manually ended listings:

    Item 198518997592 (ended manually before GTC renewal):
  DW  auct_end_dt   = 2026-09-10  ← actual end date (overwrote scheduled)
  ULP endDate       = 2026-09-23  ← original 30-day GTC schedule (not overwritten)
  ULP actualEndAt   = 2026-09-10T...  ← actual termination preserved separately

Item 1062673273 (patch shows listingStatus → ENDED):
  ULP endDate       = 2026-09-08  ← end date set when ENDED event fired
  ULP actualEndAt   = 2026-09-08T17:05:26.000Z

    For GTC listings, scheduledEndDate/scheduledEndAt reflects the current 30-day period end (rolls forward each renewal). DW sale_sched_end_dt was set at listing creation as sale_start + duration and is rarely updated. These measure different things for GTC listings.

    Cause 5 — itemRevisionDate Is Set Only on CLS Core Revisions

    GraphQL evidence: 

    # svls.graphql
"Date when the item was revised."
itemRevisionDate: DateTime @tag_directive(add: "inaccessible", gateway: "publicapi")

    This field is populated only when the ULP event was triggered by a CLS core revision — i.e., coreListingVersionId changed.

    Sample data proof:

    Trigger beforeChangePatch contains itemRevisionDate present?
    Seller revision replace: /listing/coreListingVersionId ✅ Yes
    GSP estimator update replace: .../itemEstimatorDataVersion ❌ No
    Visibility cache cleared remove: /listing/visibilitySummary ❌ No
    Photos added (CLS change) add: /listing/sellerProduct/images/N/... ✅ Yes

    DW last_modfd_dt updates on any DW ETL row write including provider-only events. These fields measure fundamentally different things:

    Field Updates when
    DW.last_modfd_dt Any DW ETL row write (seller events + provider events + operational)
    ULP.itemRevisionDate CLS core listing revision only (seller or authorized workflow)

    This explains the 14% match rate — not data quality issues but different semantic scope.

    Cause 6 — Point-in-Time Event vs T-1 Batch Snapshot

    Architecture: 

    ULP Stream Event:
  Trigger fires at T (e.g., 10:00 AM)
  → afterchangeDocumentPlain = state at time T
  → beforeChangePatch = exactly what changed at T

DW Batch:
  Runs at ~11:59 PM (SLA: results by 7:00 AM next morning)
  → dw_lstg_item = state at end of business day

    Real example (item 257569090674, qty change): 

    Yesterday's DW T-1:       qty_avail = 16
Today: ULP event fires    qty drops to 6  (patch: replace quantityAvailable)
                          afterchangeDocumentPlain.quantityAvailable = 6
Tonight's DW T-1:         qty_avail = 6  (will be updated in tonight's batch)

    This is why DW can show HIGHER values than ULP for the same day: DW = yesterday's EOD snapshot; ULP = the event that just happened today. For price and status changes, the same pattern applies — ULP is the earliest record of the change; DW will catch up at the next batch run.

    Part 3 — The marketplaceId Issue: Schema-Documented Incompatibility

    The schema explicitly documents this as a known problem (verbatim from svls.graphql):

    """
@deprecated(reason: "use marketplace")

CRITICAL COMPATIBILITY WARNING
This field returns custom SVLS-specific values that DO NOT align with
standard eBay marketplace identifier formats. There are known incompatibilities
with the GlobalIdConverter library and potentially other marketplace conversion
utilities.
"""
marketplaceId: ID

    Three representations exist simultaneously:

    Field Format Status Example
    DW.item_site_id Integer Current DW 0, 3, 77
    ULP.marketplaceId SVLS hyphen-string Deprecated EBAY-US, EBAY-GB
    ULP.marketplace Canonical enum Current EBAY_US, EBAY_GB

    The sample data shows both marketplaceId and marketplace coexisting: 

    "marketplaceId": "EBAY-US",
"marketplace":   "EBAY_US"

    To join DW to ULP: DW.item_site_id → DW_SITES → GlobalId string → ULP.marketplace enum.

    Part 4 — The @fallbackToSource Migration Mechanism

    Fields with this directive read from CLS live during a migration window instead of the NuDoc cache. From defaultulpprovider.graphql:

    directive @fallbackToSource(endDate: DateTime!, startDate: DateTime!) on FIELD_DEFINITION
"""
Directive to decide the fields for fallback retrieving.
If the record modification date is less than the start date, retrieve from gateway.
Note: The time zone of the startDate and endDate is UTC.
"""

    Active windows in svls.graphql:

    Fields Window
    listingTerms, marketplace 2026-03-01 → 2026-04-15 (expired)
    acceptBestOffer, disableBuyerRestrictions, fixedPrice, actualEndAt, listingDurationInDays, many more 2026-02-16 → 2027-03-31 (still active)

    For listings modified while a fallback window is active, ULP reads from a live CLS call rather than the NuDoc cache — a potential source of subtle transient differences between what ULP serves and what DW captures from the same NuDoc source.

    Part 5 — Weight Unit Scale Difference

    GraphQL evidence (ShippingPackageSpec type in svls.graphql): 

    type ShippingPackageSpec {
  majorWeight: Decimal    # whole units (kg for Metric, lb for English)
  minorWeight: Decimal    # fractional units (grams remainder, oz remainder)
  unitOfMeasure: UnitOfMeasure
}

enum UnitOfMeasure {
  English   # lb + oz
  Metric    # kg + grams
  Invalid
}

    DW stores weight as a single integer in the smallest applicable unit: - Metric: total grams (e.g., 597000 for 597 kg) - English: total ounces (e.g., 23 oz)

    ULP stores weight decomposed into major + minor units.

    Conversion formulas: 

    Metric:  ULP.majorWeight = DW.weight / 1000
         ULP.minorWeight = DW.weight % 1000

English: ULP.majorWeight = DW.weight / 16
         ULP.minorWeight = DW.weight % 16

    Part 6 — Root Cause Reference Table

    Difference observed in comparison Root cause GraphQL evidence
    Dates off by +1 day for EU/UK/AU listings UTC vs PST/PDT scalar DateTime = RFC-3339 UTC in all schemas
    auct_end_dt ≠ endDate for manually ended listings Schema separates scheduled vs actual endDate (scheduled) + actualEndAt (actual) are distinct fields
    sale_sched_end_dt ≠ scheduledEndDate for GTC Rolling GTC period vs original schedule scheduledEndAt reflects current 30-day period
    lstg_status_id (0/1) ≠ listingStatus (ACTIVE/ENDED) Integer vs string enum enum ListingStatusEnum in svls.graphql
    lstg_curncy_id (3) ≠ currency (GBP) Integer lookup vs ISO string scalar CurrencyAlpha3Code
    shipping_type (1) ≠ costType (FLAT) Integer vs string enum enum ShippingCostPlanType
    package_size (4) ≠ packageType (PackageThickEnvelope) Integer vs string enum enum PackageType
    lstg_mthd_id (19/23) → creationMode (Add) Intentional granularity collapse enum CreationMode { Add Relist SellSimilar SellOneLikeThis }
    weight (597000) ≠ majorWeight (597) Minor unit vs major unit decomposition majorWeight + minorWeight in ShippingPackageSpec
    last_modfd_dt ≠ itemRevisionDate (14% match) Different semantic scope Field doc: "Date when the item was revised" = CLS revision only
    item_site_id (int) ≠ marketplace (EBAY_US) Integer vs enum + migration enum ListingMarketplace; CRITICAL WARNING on deprecated marketplaceId
    Price / qty / status diverge for same-day events Point-in-time vs T-1 batch ULP = state at event time; DW = end-of-day state

    Part 7 — Consumer Guidance

    Use DW_LSTG_ITEM when you need:

    • End-of-day authoritative state (price, qty, status at EOD)
    • Fine-grained listing method (lstg_mthd_id — EasyLister vs SYI3 vs API)
    • GMV and sales data (gms_lstg_curncy, cross-join to DW_CHECKOUT_TRANS)
    • PST/PDT local dates for US business day alignment
    • Historical daily aggregates and trend analysis
    • Bitmask flags (FLAGS1–FLAGS12) for operational and eligibility signals

    Use ULP stream when you need:

    • Near-real-time state (within minutes of a change)
    • Provider-enriched data not in DW: visibility, COO, compatibility, GSP detail, eBay Live, deal state
    • Self-describing field values (no lookup tables required)
    • Precise UTC timestamps for cross-timezone event timing
    • beforeChangePatch to know exactly what changed and why an event fired
    • Structured condition descriptors and global identifiers (UPC/EAN/ISBN)
    • High-precision prices (fixedPriceWithHighPrecision)

    Fields safe to join directly (always match):

    DW.item_id          = ULP.listingId
DW.slr_id           = ULP.seller.legacyUserId
DW.application_id   = ULP.applicationId
DW.leaf_categ_id    = ULP.category.primaryCategory.id
DW.item_vrsn_id     = ULP.sellerListingVersionId
DW.auct_titl        = ULP.sellerProduct.title
DW.photo_count      = len(ULP.photos[])
DW.slr_prdct_id_txt = ULP.items[0].sku
DW.watch_cnt        = ULP.items[0].watchCount

    Fields requiring translation before joining:

    DW.lstg_curncy_id  → DW_CURRENCIES lookup → ISO string = ULP.currency
DW.shipping_type   → 1=FLAT, 2=CALCULATED, 3=FREIGHT   = ULP.costType
DW.package_size    → enum lookup            = ULP.packageType
DW.item_site_id    → DW_SITES → GlobalId   = ULP.marketplace enum
DW.weight          → ÷1000 (Metric) or ÷16 (English)   = ULP.majorWeight
DW.auct_type_code  → 9=BIN, 1=AUCTION      = ULP.listingFormat

    Fields that cannot be reconciled (different semantic scope):

    DW.last_modfd_dt      ≠ ULP.itemRevisionDate   (ETL write time vs seller revision time)
DW.auct_end_dt        ≠ ULP.endDate            (actual end vs scheduled + timezone)
DW.sale_sched_end_dt  ≠ ULP.scheduledEndDate   (original schedule vs rolling GTC period)
DW.lstg_mthd_id       → ULP.creationMode       (irreversible granularity loss: 20+ → 4)
